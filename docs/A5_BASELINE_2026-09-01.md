## Allocation per `track()` — the load-bearing half

`docs/A5_BASELINE_2026-08-28.md:137` is headed *"What it does NOT establish, and this
is the larger half"*, and it is explicit that the spool figures **"would not move even
if the cost per session doubled"**, concluding that *"the allocation table above is the
load-bearing half of this file and the sweep is context."* This re-take therefore leads
with the allocation table.

`test/bench_sdk.lua`, three runs, 2000 iterations per case, head `3895863`:

| case | B/call, 3 runs | 2026-08-28 | us CPU/call |
|---|---|---|---|
| `track`, no props | 1054.7 / 1029.6 / 1047.4 | 1044.6 / 1032.2 / 1053.8 | 3.39 / 3.22 / 3.22 |
| `track`, 3 scalar props | 1232.0 / 1238.4 / 1233.9 | 1240.0 / 1234.5 / 1238.1 | 3.55 / 3.13 / 3.27 |
| `track`, nested props | 2118.2 / 2116.2 / 2115.4 | 2116.1 / 2116.2 / 2114.7 | 3.78 / 3.44 / 4.02 |

**Unchanged on every case.** Every case enqueued 2000/2000, so the bytes are
`track()`'s and not a rejected event's.

Bytes per call is the stabler instrument by a wide margin — 0.07–2 % spread within a
case, against the 1.5x swing the millisecond figures show between sittings (below).
**A BASE→FINAL delta should rest on this table.**

The three rows are still not measured from a common starting state — the cases run
sequentially with nothing resetting the queue between them, so each row's heap delta
carries a different slice of queue growth. Read down a column, not across it, exactly
as the 2026-08-28 file says.

## Spool append — context, not the load-bearing figure

Head `3895863`, median of five runs:

```
n=2000  min 0.010  p50 0.014  p95 0.035  p99 0.062  max 0.128 ms
mean 0.018 ms   total 35.8 ms across 2000 spooling appends
p95 empty(first 100) 0.050 ms   p95 full(last 100) 0.038 ms   ratio 0.8x
sys.save calls 2002   entries handed to sys.save 875250 (437.6 per append)
json.encode calls 2000 (1.0 per append)
```

⚠ **The counters are not an instrument for the C3 delta.** The harness performs
exactly 2000 one-envelope appends on any tree, so `sys.save calls` and
`json.encode calls` are fixed by the harness's own workload. They state the *shape of
one append* — and in that role they are strong, being byte-identical across all runs on
both trees and unchanged from 2026-08-28. But C3 adds automatic lifecycle events, which
changes how often batches are spooled, a cadence this harness holds fixed. These
figures would not move if the per-session cost doubled. This is the 2026-08-28
limitation restated, not a new one.

## The result, and exactly what it covers

**On the steady-state append path, `#65` and `#66` cost nothing measurable.**

The comparison is a **counterbalanced** A/B in one sitting: baseline commit `cf0c2189`
against head `3895863`, six pairs, with the within-pair order alternating AB/BA so that
run position is not confounded with side.

| pair | order | A — `cf0c2189` | B — `3895863` |
|---:|:--|---:|---:|
| 1 | AB | 0.020 | 0.018 |
| 2 | BA | 0.018 | 0.018 |
| 3 | AB | 0.022 | 0.018 |
| 4 | BA | 0.018 | 0.018 |
| 5 | AB | 0.018 | 0.017 |
| 6 | BA | 0.019 | 0.017 |

(mean ms per append; A median 0.0185, B median 0.018)

Counterbalancing was necessary, not ceremonial: **A reads 0.020 / 0.022 when it runs
first and 0.018 / 0.018 / 0.019 when it runs second**, while B sits at 0.017–0.018 in
either position. An A-then-B design would have inflated the baseline side. Head is
equal or marginally faster; there is no regression.

The harness differs between the two commits by `+7/-1`, which is a caption on one
output line plus comments — no measurement code. The sides are comparable.

### ⚠ What this does NOT cover: the migration pass

`#66` added a load-time repair pass, `migrate_spool_events` (`storage.lua:1000`, called
at `:1123`). **No measurement here reaches it.** The harness stubs `local stores = {}`
with `load = function(path) return stores[path] end`, so `sys.load` returns nil, the
client starts from a missing spool, and the timed phase appends freshly built
current-epoch envelopes. The migration only has work when loading a pre-epoch spool
holding legacy records, which this harness never supplies.

So the data supports *unchanged steady-state append cost* and **does not** support
*the name migration costs nothing*. Measuring that needs a seeded legacy spool and a
separately timed initialisation, which is not built here.

## ⚠ The 2026-08-28 millisecond figures do not reproduce

That file records `mean 0.027 / total 53.8 / p95 0.065`. Today **neither tree
reproduces it** — the baseline commit's own unchanged code measures `mean 0.018 /
total ~36 / p95 0.035`.

This was nearly reported as a 45 % regression in `#65`/`#66`. It is not one: the
counterbalanced A/B above shows the two trees equal.

**The cause is not external CPU contention, and an earlier revision of this file
claimed it was.** `os.clock()` reports process CPU time, so competing processes have no
direct path to it. Tested — three runs idle, three under eight busy loops on a 10-CPU
machine, three idle again:

```
idle        0.024 / 48.4    0.020 / 40.9    0.019 / 38.8
under load  0.019 / 38.3    0.019 / 38.8    0.020 / 40.9
idle again  0.018 / 35.6    0.018 / 36.1    0.018 / 35.9
```

**Load does not move these figures.** What the series shows is monotone settling, with
the first run of a batch highest — which is also what produced the position effect in
the counterbalanced table. The mechanism is unestablished; JIT warm-up, page cache and
frequency ramp are all consistent with it and none was measured.

What survives, and it is the load-bearing point: **the same code produces materially
different millisecond figures in different sittings.** A BASE→FINAL delta computed by
subtracting a stored figure from a fresh one measures the sitting. The instruments that
survive are the allocation table above, and a same-sitting counterbalanced A/B — which
needs the pre-C3 **commit** `cf0c2189` reachable, not merely the numbers taken from it.

The Godot baseline reached the same conclusion independently on its own curve:
*"any comparison drawn from this curve must come from one sitting."*

## What was not measured

The migration pass, as set out above. `sys.save` in this harness stores a reference and
returns without serializing, so every spool figure is the SDK's own Lua work with the
engine's durable write excluded — as on 2026-08-28, and as
`docs/SPOOL_OVERFLOW_LATENCY_BOUND.md` states.
