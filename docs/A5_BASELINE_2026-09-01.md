## Why a re-take was owed

A5-BASE is the pre-C3 performance baseline, and the plan's rule is that **any
item shipping SDK code between a BASE and its FINAL invalidates that delta.**
Two such items landed after 2026-08-28, both in the runtime and both on the path
this harness measures:

| commit | pull request | what it did |
|---|---|---|
| `afc3b67` | `#65` | Emit registered event names, remove the three that have none |
| `3895863` | `#66` | Drop legacy `session_end` instead of renaming it |

Measured over `cf0c2189..3895863`, excluding tests and documentation:

```
shardpilot/client.lua    +34/-15
shardpilot/storage.lua  +159/-5
TOTAL runtime           +193/-20
```

`storage.lua` is where the spool append lives, so this is not a formality: the
change is **on the measured path**, and it added a load-time repair pass
(`migrate_spool_events`) that did not exist when the 2026-08-28 reading was taken.
The 2026-08-28 delta is therefore void, and the window to re-take closes when C3
reaches this SDK — after that there is no pre-C3 tree left to measure.

## The result: the change did not move the append cost

The comparison that carries this conclusion is **not** this file against the
2026-08-28 file — see the next section for why that comparison is unsound. It is
an **interleaved A/B in one sitting**: the baseline commit `cf0c2189` and the head
`3895863`, each in its own worktree, alternated four times so that machine state
cannot land preferentially on one side.

| alternation | A — `cf0c2189` baseline | B — `3895863` head |
|---:|---:|---:|
| 1 | 37.6 ms | 37.2 ms |
| 2 | 36.2 ms | 35.9 ms |
| 3 | 34.9 ms | 36.3 ms |
| 4 | 35.8 ms | 34.6 ms |

The two sides are indistinguishable. `+193/-20` of runtime change, including a
new load-time migration pass, cost nothing measurable on this path.

The harness differs between the two commits by `+7/-1`, and that difference is a
**caption on one output line plus comments** — no measurement code. The sides are
therefore comparable.

### The durable numbers are the counters, not the milliseconds

Across **all 22 runs taken today**, on both trees, these were byte-identical:

```
sys.save calls 2002   entries handed to sys.save 875250 (437.6 per append)
json.encode calls 2000 (1.0 per append)
```

They are machine-independent statements about the *shape* of an append, and they
are unchanged from 2026-08-28. A BASE→FINAL delta built on these is sound. One
built on the millisecond figures is not, for the reason below.

## ⚠ The 2026-08-28 millisecond figures do not reproduce, and the cause is the laptop

`docs/A5_BASELINE_2026-08-28.md` records `mean 0.027 ms / total 53.8 ms /
p95 0.065 ms`. Today, **neither tree reproduces that** — the baseline commit's own
code now measures `mean 0.018 / total ~36 / p95 0.035`, about 45 % faster than the
figures recorded for it.

This was nearly reported here as a 45 % regression in `#65`/`#66`. It is not one.
The first batch of head runs taken today produced `total 51.0 / 53.9 / 55.4 ms` —
reproducing the 2026-08-28 figures almost exactly — because the machine was busy
with this lane's own `git fetch` and worktree creation at the time. Once it
settled, the same tree measured `34.5–37.3 ms`, and the interleaved A/B above
showed both sides equal.

So the recorded 2026-08-28 absolutes are **dominated by machine state, not by SDK
code**, and a BASE→FINAL comparison drawn between two sittings would measure the
laptop. This matches what the Godot baseline file independently concluded on its
own curve: *"any comparison drawn from this curve must come from one sitting."*

**What this costs:** the absolute millisecond figures in either baseline file
cannot carry a BASE→FINAL verdict on their own. The two instruments that can are
the machine-independent counters, and a same-sitting interleaved A/B against the
pre-C3 commit — which is why the commit `cf0c2189` must stay reachable until C3
lands here, not merely the numbers taken from it.

## What was not measured

The heap-growth table in the 2026-08-28 file (`test/bench_sdk.lua`, bytes and µs
per `track()`) was not re-taken here. It is a separate harness answering a
separate question, and nothing in `#65`/`#66` is specific to it; it is named so
that its absence is a stated gap rather than an implied pass.

`sys.save` in this harness stores a reference and returns without serializing, so
every figure above is the SDK's own Lua work with the engine's durable write
excluded — as it was on 2026-08-28, and as `docs/SPOOL_OVERFLOW_LATENCY_BOUND.md`
states.
