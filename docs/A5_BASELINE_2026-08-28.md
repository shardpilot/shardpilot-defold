## Why now

Automatic session-lifecycle events are planned for this SDK. Each one is
another spool append and another queued envelope, so **the cost of an append
before automatic collection can only be measured while it is still absent.**
Once the events land there is nowhere left to take this reading.

## Heap growth per `track()` — the number a game client actually pays

Measured with `test/bench_sdk.lua`, three runs, 2000 iterations per case:

The microsecond column is **CPU time, not elapsed time**: `measure()` brackets
the loop with `os.clock()`, which reports process CPU consumed. Scheduler
preemption and any blocking work are excluded from it, so it is the cleaner
number for comparing two builds of this SDK and the wrong one for answering
"how long did the player wait".

| case | bytes/call | spread over 3 runs | µs CPU/call |
|---|---:|---:|---:|
| `track`, no props | **1044.6 / 1032.2 / 1053.8** | **2.0 %** | 3.07 / 3.25 / 3.26 |
| `track`, 3 scalar props | **1240.0 / 1234.5 / 1238.1** | **0.4 %** | 3.69 / 3.75 / 3.39 |
| `track`, nested props | **2116.1 / 2116.2 / 2114.7** | **0.07 %** | 3.73 / 4.04 / 3.79 |

Every case enqueued 2000/2000, so the bytes are `track()`'s and not a rejected
event's.

**The three rows are not measured from the same starting state, so read them
down the column and not across it.** The cases run sequentially with a
3600-second flush interval — nothing publishes inside the measured window by
design — and nothing resets the queue between them, so they begin at roughly 50,
2,050 and 4,050 retained events. Each row's heap delta therefore carries a
different slice of queue growth and backing-table reallocation on top of
`track()`'s own cost.

Within a row the three runs are comparable, which is what the spread column
measures and what a later BASE→FINAL comparison needs. Between rows, the
props-shape difference and the queue-depth difference are confounded, so
"nested props cost 2116 against 1032" is not a clean statement of what nesting
costs.

**These are NET LIVE-HEAP GROWTH, not an allocation count, and the difference is
a floor rather than a caveat.** `measure()` collects twice, reads
`collectgarbage("count")`, runs the loop **with the collector still active**, and
reads again. Anything `track()` allocates and drops during the loop can be
collected before the second reading and vanishes from the figure. So each number
is a **lower bound** on what the call allocates — the garbage-collection pressure
a frame actually feels is at least this and may be more.

That still makes it the right axis for this comparison, because the bound is
measured the same way on both sides of it; it is the wrong number to quote as
"bytes allocated per call" anywhere else.

**Bytes per call is the durable axis; CPU microseconds are not.** Computed the
same way for both — `(max − min) / min` over the three runs:

| case | µs CPU spread | bytes spread | bytes are steadier by |
|---|---:|---:|---:|
| no props | 6.2 % | 2.09 % | **3×** |
| 3 scalar props | 10.6 % | 0.45 % | **24×** |
| nested props | 8.3 % | 0.07 % | **117×** |

An earlier revision put the latency spread at "roughly 16 %", which none of the
three triplets supports — the arithmetic was never done on the numbers in the
table beside it. The split it was arguing for survives and is now stated as the
ratio, which says more than either percentage alone: the same split the Go leg
found between allocations and time, arrived at independently on a different
runtime — and note that the Go leg's `ns/op` IS wall time, so the two are
steadier on the same axis for different reasons rather than for one.

This is the figure automatic collection moves most directly, because it is paid
per call and the change adds calls.

## What the spool sweep establishes, and how far

**Append cost was not observed to grow with backlog** across a fill sweep to the
500-entry cap.

**That is narrower than "does not grow", and the difference is the harness —
which mocks the path in two places, not one.**

`sys.save` stores a reference and returns, while the real one serialises the
whole retained record on every append: the cost most likely to scale with
backlog is exactly the one made free.

And `json.encode` is replaced by a recursive Lua encoder defined in the harness
— it walks tables, escapes strings with `gsub`, and concatenates — which runs
**inside** every timed append. So the absolute p50/p95/mean carry that encoder's
performance rather than the engine's, in the opposite direction from the
`sys.save` mock: one removes real work, the other adds substitute work, and
neither is the shipped path. The Lua
admission path also shifts the surviving arrays on each full-spool eviction,
which is proportional to backlog size and *is* included. So the honest reading
is: **no growth was visible in this store, with the durable half of the work
mocked out.**

The ratio itself is not durable either. Two runs of unchanged code gave 1.2× and
**0.7×** — the second putting the "full" window *faster* than the empty one,
which is a p95 over 100-sample windows behaving exactly as it did on the sibling
Godot harness. Read the ratio as "no large growth seen", not as a value.

The absolute figures — p50 0.020 ms, p95 0.065 ms, mean 0.027 ms — describe one
append in this mocked store. What automatic collection multiplies is the number
of `track()` calls, which the allocation table prices, and the number of batches
reaching the spool, which nothing here prices.

## What it does NOT establish, and this is the larger half

**The spool sweep does not sit on the path automatic events take.** It calls
`spool_envelopes` directly, 2000 times. In the real flow `track` only queues;
spooling happens for whole batches after a failed publish, and on persist or
shutdown. So added events raise how often *batches* are spooled — a cadence this
harness holds fixed — and these per-append figures would not move even if the
cost per session doubled.

That is why the allocation table above is the load-bearing half of this file and
the sweep is context. The per-call figure is on the path; the per-append figure
is beside it.

Batching cadence and events per session remain unmeasured here.

The harness's own caveat is inherited and repeated here rather than buried: its
`sys.save` mock **stores a reference and returns without serializing**, so every
figure above is the SDK's own Lua work with the engine's durable write excluded.
These are not end-to-end frame costs.

## Axes not varied

One machine (a laptop — not an Android or iOS device, which is where the
question studios ask actually lives), **LuaJIT standalone — which is the same interpreter family Defold embeds**, so
what is missing is the engine and the device around it, not the VM. An earlier
revision said "not the Defold engine's own VM", which misstates what was
measured and invites a reader to discount the numbers for the wrong reason: the
interpreter is right and the host is not. A mocked durable store and a
substitute JSON encoder for the sweep; three runs for the allocation table and
two for the sweep, one config, one append shape (one envelope
per append, which is what a full queue produces).
