## Why now

Automatic session-lifecycle events are planned for this SDK. Each one is
another spool append and another queued envelope, so **the cost of an append
before automatic collection can only be measured while it is still absent.**
Once the events land there is nowhere left to take this reading.

## What this establishes

**Append cost does not grow with backlog.** p95 on the last 100 appends is
1.2× the p95 on the first 100, against a backlog that went from empty to the
500-entry cap. That is the append-only property holding under
sustained overflow, measured rather than asserted.

The absolute figures — p50 0.020 ms, p95 0.065 ms, mean 0.027 ms — are what
automatic collection will move, because it multiplies the number of appends per
session rather than the cost of one.

## What it does NOT establish, and this is the larger half

**This harness measures spool-append latency.** Three axes are outside what it
observes — allocations per `track()`, batching cadence, and events per session —
and reaching them needs a different harness, which this baseline deliberately
does not build. Read every figure below as bounded to the append path.

The harness's own caveat is inherited and repeated here rather than buried: its
`sys.save` mock **stores a reference and returns without serializing**, so every
figure above is the SDK's own Lua work with the engine's durable write excluded.
These are not end-to-end frame costs.

## Axes not varied

One machine (a laptop — not an Android or iOS device, which is where the
question studios ask actually lives), one runtime (LuaJIT, not the Defold
engine's own VM), one run (no repetition, so **no variance figure** — on the same machine a repeated Go
benchmark moved `ns/op` by up to 64% between two runs, so treat every
millisecond here as a single sample), one config, one append shape (one envelope
per append, which is what a full queue produces).
