## 1. Net live-heap growth per `track()`

**What was run.** `test/bench_sdk.lua`, 2000 iterations per case, on both trees in one
sitting, four pairs with the within-pair order alternating AB/BA.

| case | A — `cf0c2189` | B — `3895863` | paired deltas (B−A) | median |
|---|---|---|---:|---:|
| no props | 1052.5 / 1023.9 / 1031.0 / 1037.2 | 1055.5 / 1041.1 / 1025.6 / 1028.6 | +3.0 / +17.2 / −5.4 / −8.6 | **−1.2 B** |
| 3 scalar props | 1238.2 / 1236.6 / 1239.6 / 1237.5 | 1235.8 / 1235.5 / 1238.7 / 1236.6 | −2.4 / −1.1 / −0.9 / −0.9 | **−1.0 B** |
| nested props | 2114.7 / 2115.7 / 2114.3 / 2114.6 | 2113.4 / 2116.0 / 2114.8 / 2115.5 | −1.3 / +0.3 / +0.5 / +0.9 | **+0.4 B** |

**What it shows.** Paired deltas, with the mean and a two-sided 95 % interval on it (n = 4,
t-based, which assumes a normality this sample size cannot demonstrate):

| case | mean | sd | 95 % CI of the mean | signs |
|---|---:|---:|---:|---|
| no props | +1.55 B | 11.52 | [−16.78, +19.88] | mixed |
| 3 scalar props | **−1.33 B** | 0.72 | **[−2.48, −0.18]** | **all four negative** |
| nested props | +0.10 B | 0.97 | [−1.44, +1.64] | mixed |

`3 scalar props` is the one case with a consistent direction — deltas −2.4 / −1.1 / −0.9 / −0.9,
all negative. An earlier revision said no delta kept its sign across all four pairs, which is
false for that case.

⚠ **No detection is claimed, and the reason is the precision of the input rather than the
statistics.** `test/bench_sdk.lua:385` prints `%10.1f B/call`, so **every value above is
already rounded to 0.1 B**, both sides independently — leaving each paired delta uncertain by
up to ±0.1 B, which the interval does not propagate. Shifting the deltas differentially inside
their rounding bins (`−2.5 / −1.0 / −0.8 / −0.8`) gives mean −1.275, sd 0.818 and an upper
endpoint of **≈ +0.03 B**: zero is inside. **"The interval excludes zero" is a property of the
rounding, not of the measurement.**

That is more fundamental than multiplicity, which also applies: three cases were compared, and
a Bonferroni correction (α = 0.0167, df = 3) widens the scalar interval to about [−3.1, +0.4] B
on its own. Either way — **one case shows a consistent direction of roughly a tenth of a
percent, and this instrument cannot establish that it differs from zero.**

**No equivalence margin is defined here, and none of the above is one.** An interval containing
zero is not evidence of equivalence — the no-props interval spans ±19 B, so a repeatable ~1 %
increase remains entirely compatible with these samples. Ruling that out needs a margin stated
in advance and enough repetitions to test against it; a later BASE→FINAL acceptance decision
should set the margin **first** and size the runs to it.

**What it does not show.** These are **net live-heap growth, not an allocation count.** The
harness runs `collectgarbage("collect")` twice, reads `collectgarbage("count")` before and
after, and differences them with the collector live — so anything allocated and collected
inside the loop is invisible. `A5_BASELINE_2026-08-28.md:72` states this in capitals and `:77`
calls the figure a **lower bound**; both are restored here. A regression purely in transient
allocation or GC pressure would not appear in this table.

**Compare across each row, not down the columns.** A row is one case measured on both trees,
which is the comparison; a column mixes three different property shapes measured at three
different queue depths, because the cases run sequentially with nothing resetting the queue
between them. ⚠ An earlier revision of this file said the opposite — it carried a sentence over
from `A5_BASELINE_2026-08-28.md`, whose table has a different layout, and so pointed readers at
exactly the confounded comparison the sentence beside it warns about.

⚠ An earlier revision of this file compared **these** runs against the **stored** 2026-08-28
figures, which is the cross-sitting subtraction this document argues against. The table above
is same-sitting and counterbalanced.

## 2. Spool append

**What was run.** `test/bench_spool_append.lua`. Descriptive figures are the median of five
head runs. The comparison is six pairs, counterbalanced AB/BA, one sitting.

Descriptive, head `3895863`:

```
n=2000  min 0.010  p50 0.014  p95 0.035  p99 0.062  max 0.128 ms
mean 0.018 ms   total 35.8 ms across 2000 spooling appends
p95 empty(first 100) 0.050 ms   p95 full(last 100) 0.038 ms
sys.save calls 2002   entries handed to sys.save 875250 (437.6 per append)
json.encode calls 2000 (1.0 per append)
```

Comparison, mean ms per append:

| pair | order | A — `cf0c2189` | B — `3895863` |
|---:|:--|---:|---:|
| 1 | AB | 0.020 | 0.018 |
| 2 | BA | 0.018 | 0.018 |
| 3 | AB | 0.022 | 0.018 |
| 4 | BA | 0.018 | 0.018 |
| 5 | AB | 0.018 | 0.017 |
| 6 | BA | 0.019 | 0.017 |

**What it shows.** **No regression was observed at the reported precision** in the Lua work
performed before the mocked save. Paired deltas are −0.002 / 0.000 / −0.004 / 0.000 / −0.001 /
−0.002 ms: mean −0.0015, 95 % CI [−0.0031, +0.0001], which includes zero. ⚠ **Two pairs are
ties at 0.001 ms resolution**, and a tie at the printed precision can hide a difference in
either direction beneath it. This is not equivalence, no margin was defined, and a small
systematic increase remains untested. It is also not a statement about append cost on a real
host, because the durable write is stubbed out — see the exclusions below.

**On the ordering effect, with every observation.** A running **first** reads
0.020 / 0.022 / **0.018**; A running **second** reads 0.018 / 0.018 / 0.019. ⚠ An earlier
revision listed only 0.020 / 0.022 for the first position, omitting the third — which is
precisely the value overlapping the second-position range — and so overstated the effect.
With all six shown, the comparison is **two higher and one LOWER** — 0.018 against 0.019 in
the third — not "equal in the third", as a further revision of this same sentence claimed.
That reading justifies counterbalancing as a **precaution against a confound this sample
cannot rule out**, and evidences no position effect at all. The design was counterbalanced
either way, so whatever position does, it cannot land preferentially on one side.

**What it does not show.** Three separate exclusions, and together they are most of what
`#65` and `#66` changed:

- **The migration pass is never executed.** `migrate_spool_events` (`storage.lua:1000`, called
  at `:1123`) is **introduced by `#65`, not `#66`** — as are `spool_wire_name_epoch` and the
  `wire_names` record field; `#66` changes the migration from renaming to dropping and adds
  epoch/drop handling. The harness stubs `local stores = {}` with
  `load = function(path) return stores[path] end`, so `sys.load` returns nil and the pass has
  nothing to migrate.
- **`sys.save` is not the only mocked host work.** `approx_envelope_bytes`
  (`storage.lua:844`) calls `json.encode` when a `json` global exists, and it is invoked at
  `:1164` inside the spool path — so it runs in **every timed append**. The harness installs a
  **recursive Lua encoder** at `test/bench_spool_append.lua:41-62`; Defold ships an engine
  encoder. The A/B comparison survives, since the same shim is on both trees and the envelopes
  are identical, but **the absolute figures here and in §3 include substitute encoder work that
  does not ship**, and are properties of this harness rather than of the SDK's cost on a
  device.
- **The renamed events are never emitted.** `make_envelope` builds
  `event_name = "level_completed"` on both sides, so `#65`'s rename of `session_end` to
  `app.session_ended` is not exercised. Both sides serialize identical payloads.
- **Per-append success is not asserted.** Line 108 calls `client:spool_envelopes({ env })` and
  discards the return, so a run in which every append returned false would still print its
  summary. The runs here are **validated from their counters** — `sys.save calls 2002` and
  875250 entries are positive evidence that work occurred — not asserted by the harness.
- **The persisted record is NOT identical between the sides, and its serialization is mocked
  away.** The `wire_names` field written by `write_spool` carries a different epoch value
  between the trees. The harness's `sys.save`
  (lines 24–30) only counts entries and retains a table reference — it never serializes — so
  that added field costs B nothing here. On a real Defold host, where `sys.save` serializes,
  it would not be free. The identical-payload statement above holds for the **envelope**
  (`level_completed` on both sides) and **not** for the persisted record.

What the comparison therefore supports is narrower than "the changes cost nothing", and is
still worth having: **the load-path machinery added across `#65` and `#66` together imposes no
measurable cost on the common append that does not use it.** It is stated for the combined
base-to-head delta because this experiment compares `cf0c2189` with `3895863` and cannot
apportion an effect between the two commits inside that range.

⚠ **The counters are not an instrument for the C3 delta.** The harness performs exactly 2000
one-envelope appends on any tree, so `sys.save` and `json.encode` counts are fixed by its own
workload. They describe the shape of one append — and are byte-identical across every run on
both trees — but C3 changes how often batches are spooled, a cadence this harness holds fixed.
`A5_BASELINE_2026-08-28.md:137` is headed *"What it does NOT establish, and this is the larger
half"* and says exactly this.

## 3. The 2026-08-28 millisecond figures do not reproduce

**What was run.** Both trees, this sitting, plus a counterbalanced interference experiment.

That file records `mean 0.027 / total 53.8 / p95 0.065`. Today the baseline commit's own
unchanged code measures `mean 0.018 / total ~36 / p95 0.035`.

Interference, `I L L I I L L I` so load is not confounded with run epoch. **The `L`
condition is eight concurrent `bash` busy-loops (`while :; do :; done`) started before the run
and killed after it, on a 10-CPU machine, with the benchmark competing as a ninth process.**
No CPU utilisation, frequency or per-core placement was recorded, so the stimulus is defined by
its command and worker count only — total ms:

```
I 38.0   L 39.0   L 39.4   I 36.5   I 34.1   L 39.7   L 36.2   I 36.0
idle median 36.25 (n=4)      loaded median 39.20 (n=4)
```

**What it shows.** The same code produces materially different millisecond figures in
different sittings — roughly 50 % apart — and external CPU load shows a small apparent effect
of about 8 % on medians, far too small to account for that gap.

**What it does not show.** The cause. Ranges overlap (idle max 38.0, loaded min 36.2) at n=4
per condition, so the 8 % is an apparent effect, not an established one — contention is
neither excluded nor sufficient. And the 8 % belongs to **this** stimulus: eight busy-loops is
one arbitrary point on an unmeasured axis, so it bounds what that load did and not what
contention in general can do. A heavier or differently-shaped load was not tried. Two earlier revisions of this file each offered a mechanism —
first competing `git` work, then batch warm-up — and **both are withdrawn rather than hedged**,
because neither was tested and the one that was tested came out the other way.

**The consequence that does hold** is the load-bearing point of this file: **a BASE→FINAL
delta computed by subtracting a stored millisecond figure from a fresh one is CONFOUNDED** —
the subtraction contains the sitting effect *and* any genuine code effect, with no way to
separate them. ⚠ An earlier revision said such a delta "measures the sitting", which
overshoots in the other direction: that phrasing would license attributing a real regression
entirely to the environment. What the same-code discrepancy establishes is that the delta
**cannot isolate the code change** — not that there is nothing but environment in it. The instruments that survive are section 1's table and a same-sitting
counterbalanced A/B against `cf0c2189`, which stays reachable as an ancestor of `main`.

The Godot baseline reached the same conclusion independently on its own curve: *"any comparison
drawn from this curve must come from one sitting."*
