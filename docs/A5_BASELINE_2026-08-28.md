## Why now

Automatic session-lifecycle events are planned for this SDK. Each one is
another spool append and another queued envelope, so **the cost of an append
before automatic collection can only be measured while it is still absent.**
Once the events land there is nowhere left to take this reading.

## Allocation per `track()` — the number a game client actually pays

Measured with `test/bench_sdk.lua`, three runs, 2000 iterations per case:

| case | B/call | spread over 3 runs | µs/call |
|---|---:|---:|---:|
| `track`, no props | **1032.2** | — | 3.25 |
| `track`, 3 scalar props | **1240.0 / 1234.5 / 1238.1** | **0.4 %** | 3.69 / 3.75 / 3.39 |
| `track`, nested props | **2116.1 / 2116.2 / 2114.7** | **0.07 %** | 3.73 / 4.04 / 3.79 |

Every case enqueued 2000/2000, so the bytes are `track()`'s and not a rejected
event's.

**Bytes per call is the durable axis; microseconds is not** — 0.07–0.4 % against
roughly 16 %. That is the same split the Go leg found between allocations and
wall time, arrived at independently on a different runtime.

This is the figure automatic collection moves most directly, because it is paid
per call and the change adds calls.

## What the spool sweep establishes, and how far

**Append cost was not observed to grow with backlog** across a fill sweep to the
500-entry cap.

**That is narrower than "does not grow", and the difference is the harness.**
The store is a mock: its `sys.save` stores a reference and returns, while the
real one serialises the whole retained record on every append — the cost most
likely to scale with backlog is exactly the one made free here. The Lua
admission path also shifts the surviving arrays on each full-spool eviction,
which is proportional to backlog size and *is* included. So the honest reading
is: **no growth was visible in this store, with the durable half of the work
mocked out.**

The ratio itself is not durable either. Two runs of unchanged code gave 1.2× and
**0.7×** — the second putting the "full" window *faster* than the empty one,
which is a p95 over 100-sample windows behaving exactly as it did on the sibling
Godot harness. Read the ratio as "no large growth seen", not as a value.

The absolute figures — p50 0.020 ms, p95 0.065 ms, mean 0.027 ms — describe one
append in this mocked store. What automatic collection multiplies is the number
of `track()` calls, which the allocation table prices, and the number of batches
reaching the spool, which nothing here prices.

## What it does NOT establish, and this is the larger half

**The spool sweep does not sit on the path automatic events take.** It calls
`spool_envelopes` directly, 2000 times. In the real flow `track` only queues;
spooling happens for whole batches after a failed publish, and on persist or
shutdown. So added events raise how often *batches* are spooled — a cadence this
harness holds fixed — and these per-append figures would not move even if the
cost per session doubled.

That is why the allocation table above is the load-bearing half of this file and
the sweep is context. The per-call figure is on the path; the per-append figure
is beside it.

Batching cadence and events per session remain unmeasured here.

The harness's own caveat is inherited and repeated here rather than buried: its
`sys.save` mock **stores a reference and returns without serializing**, so every
figure above is the SDK's own Lua work with the engine's durable write excluded.
These are not end-to-end frame costs.

## Axes not varied

One machine (a laptop — not an Android or iOS device, which is where the
question studios ask actually lives), one runtime (LuaJIT, not the Defold
engine's own VM), a mocked durable store for the sweep, three runs for the
allocation table and two for the sweep, one config, one append shape (one envelope
per append, which is what a full queue produces).
